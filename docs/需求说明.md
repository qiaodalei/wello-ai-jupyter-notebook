## 1. 背景与目标

用户希望在一个网页里完成「提需求 → AI 写说明和代码 → 在 Jupyter 单元格里执行 → 把运行结果再喂给模型继续改」的闭环，同时保留完整的 Jupyter Notebook 手工编辑与运行能力。

需求范围就是「所有适合在 Notebook 里做的事」，不限于数据科学：数据清洗与分析、图表可视化、机器学习训练、科学计算与符号推导、算法实现与验证、文本处理、文件批处理与格式转换、调接口抓数据、学习某个库的用法、以及各种一次性小脚本。

典型例子：用户说「用 MNIST 训练一个数字识别模型」，系统应自动生成讲解、代码、依赖安装、训练与评估单元格，执行后根据准确率、报错或图表继续迭代；用户说「用 sympy 解这个方程再画出曲线」或「把这一批 csv 合并成一个 excel」，同样走完写入 → 执行 → 看结果 → 修正的闭环，只是规模小得多——投入应与需求本身的大小匹配。

### 1.1 要解决的问题

- 从想法到可运行实验之间，用户仍要手动拆步骤、写样板代码、处理报错。
- 普通聊天式 AI 只能给代码片段，不能真正跑起来，也无法根据执行结果自我修正。
- 传统 Jupyter 功能完整，但缺少「按任务驱动的 Agent 工作流」。

### 1.2 产品目标

做一个**可执行的 AI 实验工作台**：对话驱动生成 Notebook，内核真实执行，结果回流给模型；用户随时可以像用 Jupyter 一样接管单元格。

MVP 成功标准：

1. 用户用自然语言提出一个可以在 Notebook 里完成的任务（数据分析、可视化、机器学习、数学计算、算法验证、文件处理、脚本等）。
2. AI 在 Notebook 中生成 Markdown + Code 单元格。
3. 代码在 Python 内核中执行，输出（stdout、错误、图表）可见。
4. 执行结果自动回到模型，模型能据此修复错误或继续下一步。
5. 用户可手动增删改单元格、单独运行、保存 / 打开 `.ipynb`。

## 2. 产品定位

**一句话：** 带 Agent 闭环的 Jupyter Notebook，而不是「会写代码的聊天框」。

| 维度 | 说明 |
|---|---|
| 是什么 | Web 端 Notebook 编辑器 + Python 内核 + AI Agent |
| 不是什么 | 纯聊天机器人、Colab 克隆、多用户协作平台、完整 IDE |
| 主场景 | 教学演示、个人实验、快速原型、数据探索 |
| 核心差异 | 生成物落在真实单元格里，执行结果构成下一轮模型输入 |

### 2.1 目标用户

| 角色 | 诉求 | 优先级 |
|---|---|---|
| 学生 / 自学用户 | 听懂步骤，看见能跑的代码和结果 | P0 |
| 数据科学 / ML 工程师 | 少写样板，快速试假设，自己改细节 | P0 |
| 教师 / 演示者 | 现场根据问题生成可演示 Notebook | P1 |
| 研究人员 | 可复现实验、保存版本、导出 | P1 |

### 2.2 使用原则

- **Notebook 是唯一真相源。** AI 的产出必须写入单元格，而不是只出现在聊天记录里。
- **用户永远可接管。** 任何单元格都可手动编辑、运行、删除；AI 不得锁死内容。
- **先跑通再优化。** Agent 优先保证可执行，再追求结构优雅。
- **结果驱动下一轮。** 没有执行反馈，不算完成一次 Agent 回合。

## 3. 核心用户场景

### 场景 A：从一句话生成完整实验（主路径）

1. 用户新建 Notebook，在对话栏输入：「如何使用 MNIST 训练一个数字识别模型」。
2. Agent 规划步骤：环境检查 → 加载数据 → 构建模型 → 训练 → 评估 → 可视化。
3. 依次写入 Markdown 说明单元格和 Code 单元格。
4. 自动（或经用户确认后）按序执行代码单元格。
5. 若某格报错（缺包、路径错误、shape 不匹配），Agent 读取 traceback，插入修复单元格或改写原单元格，再重跑。
6. 训练完成后，准确率、loss 曲线、样例预测图出现在输出区；Agent 用简短 Markdown 总结结果与可改进点。

### 场景 B：在已有 Notebook 上追问

用户已有数据加载代码。继续说：「把模型换成 CNN，并画出混淆矩阵。」  
Agent 读取当前单元格与近期输出，在合适位置追加或修改单元格，而不是从头重写整本。

### 场景 C：纯手工 Jupyter

用户不跟 AI 说话，自己增删单元格、Shift+Enter 运行、改 Markdown、保存文件。体验应接近经典 JupyterLab / VS Code Notebook。

### 场景 D：执行失败后的人机协作

代码跑挂后，用户可：

- 让 AI 根据报错自动修；
- 自己改一行再让 AI 从当前状态继续；
- 忽略该格，手动运行后续格子。

## 4. 功能需求

### 4.1 AI Agent（P0）

#### 4.1.1 需求输入

- 页面内对话栏：支持多轮自然语言。
- 支持把当前 Notebook 上下文（单元格源码、最近一次运行输出摘要、内核状态）发给模型。
- 支持用户指定约束，例如：「只用 PyTorch」「不要下载过大的数据集」「解释写中文」。

#### 4.1.2 单元格生成

Agent 必须能产出：

| 单元格类型 | 用途 | 要求 |
|---|---|---|
| Markdown | 讲解、步骤、结论 | 结构清楚，避免把代码写进 Markdown |
| Code | 可执行 Python | 可独立或按序运行；依赖显式安装 |
| 后续可扩展 Raw | 较少使用 | MVP 可不做写入，只做兼容显示 |

生成规则：

- 一次任务拆成多个单元格，而不是一个巨大 code cell。
- Markdown 与 Code 交错：先说明再代码。
- 长时间任务（训练）要有进度打印或分步单元格，避免「一个 cell 跑 10 分钟且无输出」。
- 需要第三方库时，单独给出 `pip install` 单元格，并说明已安装则跳过。

#### 4.1.3 执行与反馈闭环

这是产品的核心循环：

```
用户需求
  → Agent 规划
  → 写入 Markdown / Code 单元格
  → Kernel 执行
  → 收集 stdout / stderr / display / 错误
  → 将结果摘要回传 Agent
  → 决定：继续 / 修复 / 向用户提问 / 结束
```

反馈给模型的内容应包括：

- 执行单元格的 `id`、源码、退出状态；
- stdout / stderr 截断后的文本；
- 若有图像，给出「已生成图像」说明，必要时附缩略或文字描述（MVP 可用「存在 image/png 输出」）；
- 内核是否仍存活。

Agent 根据反馈应能：

- 修复 ImportError / 语法错误 / shape 错误；
- 改超参数或训练轮数后重跑；
- 发现结果不合理时补充诊断单元格；
- 多次失败后停止并说明原因，而不是死循环。

#### 4.1.4 Agent 控制

- **运行策略：** 自动执行新代码单元格 / 仅生成不执行 / 逐步确认后执行。MVP 默认「生成后自动执行代码单元格」。
- **停止：** 用户可随时停止 Agent 与内核执行。
- **可见过程：** 显示当前在「规划 / 写单元格 / 执行 / 阅读输出 / 修复」。
- **循环上限：** 单次任务最多自动修复 N 轮（建议默认 5），超出后交还用户。

#### 4.1.5 模型与工具约定（产品层）

- 模型通过统一 LLM 接口调用，API Key 由本地环境变量或设置页配置，不写死在前端。
- 模型通过统一 LLM 接口调用，采用流式返回：思考过程与正文边生成边显示，不让用户对着一个静态的「thinking」等待。
- Agent 可使用的工具（逻辑工具，不一定是独立进程）：
  - `read_notebook`：读全部或指定单元格；
  - `add_step`：加一步 = 一个 markdown 说明 + 一个 code 单元格，并立刻执行、返回真实输出；
  - `replace_cell` / `delete_cells`：改写或删除已有单元格（修 bug 走这条）；
  - `run_cell`：重跑指定单元格；
  - `ask_user`：信息不足时提问。
- **一轮只能加一步。** 这是产品层的硬约束，不只是提示词要求：Agent 必须先读到上一步的真实输出，才能写下一步。
  用 Notebook 的意义就在于一步步讲解或一步步调试，不允许一次把所有单元格写完再统一执行。
- **每一步都必须有 markdown**，缺了后端直接驳回。一步只做一件能单独看结果的事；代码超过 25 行左右就要拆成两步。
- **markdown 是交付物，不是过程播报。** `#` 作 notebook 标题、`##` 作各小节，标题连起来就是这份 notebook 的目录；
  正文写方法与取舍，关键结果跑出来后回填进对应小节。行动播报（「接下来我要…」）、自我交代、调试痕迹都不进单元格，
  改由对话回复承担。验收标准：删掉全部对话记录，单独把 `.ipynb` 交给他人，仍能读懂做了什么、结论是什么。

#### 4.1.6 会话与上下文（产品层）

- **每个 notebook 一个会话**：切换文件即切换上下文；另存改名时上下文随之迁移，删除文件时上下文一并清除。
- **运行与 notebook 绑定**：一次任务从发起那一刻起绑定到当前 notebook，其单元格写入、上下文归属和流式事件
  都只属于该 notebook；其他 notebook 的对话面板不得出现它的任何输出（事件按 notebook 标记并过滤）。
- **多本并行可用**：可同时打开多本并同时运行。切换 notebook 只改变「看哪一本」，不打断任何运行，
  不需要用户确认；侧栏标示每一本各自的运行状态。唯一禁止的操作是删除正在运行的那一本。
- **每本一个内核**：变量互不可见，一本的长任务不阻塞另一本的执行；重启内核只影响当前这一本。
  内核按需启动（首次执行时），常驻数量有上限，回收时优先淘汰最久未用的；正在查看和正在运行的不淘汰。
- **切换不丢数据**：所有已打开的文档同时驻留内存，切换不重读磁盘；切换仍会顺手落盘，便于崩溃后恢复。
- **上下文窗口为最近 5 轮 QA**，避免长会话拖慢响应、稀释当前意图。
- **可清空当前上下文**：只清对话，不动单元格；该 notebook 自己运行中时禁止清空（其他本运行不受影响）。
- **思考过程可见但可收起**：流式展示，一轮结束折叠为可展开区块，不直接丢弃。
- Agent **不得**在未写入 Notebook 的情况下声称「已经训练完成」。结论必须来自真实输出或明确告知「尚未执行」。

### 4.2 Jupyter Notebook 基础能力（P0）

下列能力即使关掉 AI，也应可用。

#### 4.2.1 单元格模型

- 类型：Code、Markdown；MVP 可只读写这两种，打开他人 `.ipynb` 时 Raw 以只读或降级显示。
- 每个单元格有稳定 `id`。
- 状态：idle / running / queued / ok / error。
- 支持源码编辑（等宽字体、基础语法高亮、Tab 缩进）。
- Markdown 渲染：标题、列表、链接、代码块、公式（MVP 可用 KaTeX，复杂宏可后置）。

#### 4.2.2 单元格操作

- 在上方 / 下方插入 Code 或 Markdown；
- 删除、复制、剪切、粘贴；
- 上移 / 下移；
- 类型切换（Code ↔ Markdown）；
- 选中当前单元格；
- 清空输出；
- 合并相邻同类单元格、拆分（P1，MVP 可后置拆分）。

#### 4.2.3 运行控制

- 运行当前单元格；
- 运行当前及之后；
- 运行全部；
- 中断执行；
- 重启内核（可选：重启后运行全部）。
- 代码单元格执行序号 `In [n]`，与 Jupyter 习惯一致。
- 队列执行：连点运行时按顺序排队，不并行抢内核。

#### 4.2.4 输出展示

至少支持：

- 流式文本（stdout / stderr），执行中增量刷新；
- 错误 traceback（与成功输出视觉区分）；
- 静态图 `image/png`、`image/jpeg`；
- HTML 表格（pandas 预览可先用 text/plain 或简单 HTML）；
- 执行时间显示。

P1：交互 widget、Plotly、IFrame、LaTeX 输出。

#### 4.2.5 内核

- **每个打开的 Notebook 对应一个本地 Python 内核**，互相隔离；执行队列也各自独立。
- 支持 `!pip install` 或等价安装方式（需在安全策略中约束）。
- 内核重启后变量清空，单元格源码保留。
- 显示内核状态：未启动 / 空闲 / 忙碌 / 断开。

#### 4.2.6 文件与 Notebook 生命周期

- 新建空白 Notebook；
- 打开 `.ipynb`（nbformat v4）；
- 保存 / 另存为；
- 自动保存（建议每 30s 或内容变更后防抖）；
- 导出 `.ipynb` 下载；
- 浏览器刷新后尽量恢复未保存内容（localStorage 或服务端草稿）。

P1：工作区内上传 csv / 图片等数据文件，供代码读取。

#### 4.2.7 快捷键（P0 最小集）

对齐 Jupyter 习惯，降低迁移成本：

| 快捷键 | 行为 |
|---|---|
| Shift+Enter | 运行当前单元格并选中下一格 |
| Ctrl/Cmd+Enter | 运行当前单元格 |
| Alt+Enter | 运行并在下方插入新格 |
| A / B（命令模式） | 上方 / 下方插入 |
| DD（命令模式） | 删除单元格 |
| M / Y | 转为 Markdown / Code |
| Enter / Esc | 编辑模式 / 命令模式 |

MVP 若时间不够，至少保证 Shift+Enter 与插入 / 删除。

### 4.3 界面结构（P0）

建议三栏，允许折叠：

1. **左侧：** Notebook 文件列表（MVP 可先做当前文件 + 新建）。
2. **中间：** Notebook 画布（单元格流）。
3. **右侧或底部：** AI 对话与 Agent 过程。

其它 UI：

- 顶栏：文件名、保存、内核状态、运行全部、停止、AI 开关。
- 单元格左侧：运行按钮、拖拽手柄（拖拽排序为 P1）。
- 空状态：提示「描述你想做的实验，或手动添加单元格」。

布局原则：对话是入口，Notebook 是工作区；生成内容必须能在中间画布里看见，不能只存在于聊天气泡。

### 4.4 设置（P0 最小）

- LLM API Base URL、API Key、模型名；
- Agent 是否自动执行代码；
- 最大自动修复轮数；
- 主题：浅色（P1 深色）。

密钥只保存在本地或服务端环境，不进入 `.ipynb`。

## 5. 关键交互流程

### 5.1 主流程：AI 生成并执行

```text
用户输入需求
        │
        ▼
Agent 读取当前 notebook 快照
        │
        ▼
规划步骤（对用户可见的简短计划）
        │
        ▼
循环：写入 1..k 个单元格
        │
        ▼
对每个新 Code 单元格：入队执行
        │
        ├─ 成功 → 收集输出 → 判断是否继续下一步
        └─ 失败 → 把错误送回模型 → 修改该格或插入修复格 → 重跑
        │
        ▼
写入总结 Markdown，结束本轮
        │
        ▼
用户可继续追问或手工改代码
```

### 5.2 冲突处理

| 情况 | 行为 |
|---|---|
| Agent 正在写，用户同时编辑同一单元格 | 以用户编辑为准，Agent 暂停该格并提示冲突 |
| 用户点击停止 | 停止后续生成与排队执行，已运行的格可中断内核 |
| Notebook 为空且用户直接运行 | 无操作或提示没有代码单元格 |
| 模型返回非单元格文本 | 作为聊天回复展示，不污染 Notebook；同时尽量要求模型走工具写入 |

## 6. 信息架构与数据

### 6.1 Notebook 文件

遵循 Jupyter `nbformat` v4，保证用 JupyterLab / VS Code 也能打开。

每个 code cell 保存：

- `source`
- `outputs`
- `execution_count`
- `metadata`（可记录 `ai_generated: true`、任务 id，便于追溯）

### 6.2 会话状态（运行时，不必全部落盘）

- 内核 id、执行队列；
- Agent 当前任务 id、轮次、停止标志；
- 对话历史（可与 notebook 分开存储）。

### 6.3 对话与 Notebook 的关系

- 一个浏览器会话对应一份当前 Notebook + 一组对话。
- 保存 Notebook 时不强制把完整聊天记进 `.ipynb`（避免文件膨胀）。
- P1：对话可与文件关联，下次打开同一 notebook 恢复侧栏历史。

## 7. 非功能需求

### 7.1 性能

- 单元格编辑输入延迟应可忽略（本地编辑，不每键请求模型）。
- stdout 流式刷新间隔建议 ≤ 200ms 合并一次。
- 单次 LLM 请求需有超时与可取消。
- 训练等长任务不得卡住整个 UI；停止按钮始终可点。

### 7.2 可靠性

- 内核崩溃后可重启，不丢单元格源码。
- 自动保存失败要提示，不能静默丢数据。
- Agent 循环必须有硬上限和停止开关。

### 7.3 安全（MVP 按「个人本机 / 受信环境」设计）

- 代码在内核中执行，等同用户本机跑 Python，需在界面明确提示。
- MVP **不面向公网多租户**；若以后托管执行，需加沙箱、资源限额、网络策略。
- API Key 不明文写入仓库或 notebook。
- `!` shell 与任意命令在托管场景下默认关闭（本机 MVP 可开）。

### 7.4 兼容

- 现代 Chromium / Firefox / Safari 最近两个大版本。
- 导入标准 `.ipynb`；导出后可被官方 Jupyter 打开。

### 7.5 国际化

- UI 与 Agent 默认中文；代码注释 / 变量名按用户要求，默认中文讲解 + 英文代码标识符。

## 8. 范围与分期

### 8.1 MVP（第一期，必须交付）

- Web 页面：对话 + Notebook 画布。
- Markdown / Code 单元格的增删改、运行、输出展示。

- Agent：根据自然语言写入单元格 → 执行 → 读输出 → 有限轮修复。

## 9. 技术方向（需求约束，非最终方案）

实现阶段可替换，但需求上有这些约束：

| 层次 | 约束 | 候选 |
|---|---|---|
| 前端 | 单元格编辑 + Markdown 渲染 + 输出区 | React / Vue；编辑器可用 CodeMirror 6 |
| Notebook 格式 | 必须 nbformat v4 | 自研 JSON 需能导入导出 `.ipynb` |
| 内核 | 真实执行 Python，支持 Jupyter 消息协议更佳 | Jupyter Kernel (ipykernel) + jupyter_client / Kernel Gateway |
| Agent | 工具调用，而不是一次吐完整 JSON 再解析失败 | LLM function/tool calling |
| 后端 | 协调内核、文件、LLM，避免浏览器直连内核 | Python（FastAPI 等） |
| 通信 | 执行流式输出、Agent 过程 | WebSocket 或 SSE |

不建议第一期用「把代码 eval 在 Node 里」或「只把代码发给外部 Colab」冒充内核。

## 10. 验收标准

以「MNIST 数字识别」为黄金用例，同时覆盖手工 Jupyter。

### 10.1 黄金用例

前置：用户已配置可用的 LLM。

1. 新建 Notebook，输入：「如何使用 MNIST 训练一个数字识别模型，用 PyTorch，轮数少一点以便尽快跑完，解释用中文。」
2. 系统在 1 分钟内开始写入单元格（网络与模型速度允许差异，但必须有进度）。
3. 出现至少：任务说明 Markdown、安装/导入、数据加载、模型定义、训练、评估。
4. 代码单元格被执行；若缺依赖，Agent 能安装或给出失败原因并停止。
5. 若训练代码报错，Agent 至少自动修复 1 次或明确说明无法继续。
6. 成功路径下，输出中可见 loss / accuracy 类结果，且有一段中文总结。
7. 用户手动改 `epochs` 后 Shift+Enter 能重跑该格。
8. 保存后的 `.ipynb` 用官方 Jupyter 打开，源码与输出仍在。

### 10.2 基础 Jupyter 验收

- 插入 Markdown，编写标题，渲染正确；
- 插入 `print(1+1)`，运行得到 `2`；
- 制造语法错误，输出区显示 traceback，内核仍可运行下一格；
- 中断一个 `time.sleep(60)`；
- 重启内核后，未重新运行则变量不可用。

### 10.3 Agent 行为验收

- 关闭「自动执行」时，只写单元格不跑；
- 点击停止后不再新增单元格；
- 达到最大修复轮数后停止并提示；
- 追问「画出几张预测错误的样本」时，基于现有变量追加单元格，而不是无故清空全本。

## 11. 风险与开放问题

| 风险 / 问题 | 影响 | 建议 |
|---|---|---|
| 模型一次生成不可运行的代码 | 用户觉得「还是不能跑」 | 强制执行反馈 + 修复轮次 |
| MNIST / 深度学习依赖体积大、训练慢 | 演示卡死 | 验收用极少 epoch、小 batch；可提供 CPU 友好默认 |
| 本机执行任意代码的安全误解 | 被当成托管 SaaS | UI 明确「在你的环境执行」 |
| 执行输出过大撑爆上下文 | Agent 变笨或超时 | 截断、摘要、只传失败格全文 |
| 用户与 Agent 同时改同一格 | 丢编辑 | 冲突时暂停 Agent |
| LLM 费用与延迟 | 体验差 | 流式展示过程；设置里换模型 |

待产品确认（实现前拍板）：

1. 默认框架：PyTorch 还是 TensorFlow，或由模型自选？
2. 内核跑在用户本机，还是项目自带后端容器？
3. 第一期是否需要登录，还是纯本地单用户？
4. 对话栏默认贴右侧还是底部？

**建议默认：** PyTorch、本地后端 + ipykernel、无登录单用户、对话栏右侧。
